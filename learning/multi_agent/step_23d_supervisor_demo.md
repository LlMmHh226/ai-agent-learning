# 23D 延伸：受控主管与跨轮待办

## 学习目标

观察主管的候选动作如何受任务依赖约束，以及下一轮如何继续同一个待办。

## 前置知识

完成 [23D 一次路由](step_23d_router.md)。想把状态保存跨进程，另读 [会话持久化](../postgresql/step_06_conversation_persistence.md)。

## 文件职责

[主管与续办示例](step_23d_supervisor_demo.py) 用 `ReturnCase` 保存任务和证据；`ready_actions()` 计算允许动作，`accept_proposal()` 检查候选；等待用户补充的快照保存在本进程内。它只读取样例订单和政策，不提交退货申请。

## 具体输入与执行过程

首轮「看看订单10001能不能退」 → 建立 `return-1` → 拒绝提前查政策的候选，先核实订单 → 读取退货政策 → 输出需补签收期限和商品状况。补充「昨天签收，没拆封」在例子中仅更新期限，不推断商品状态；确定完好且不影响二次销售后，复用同一个待办汇总。另一个订单不会接收本订单的资料。

## 运行与预期结果

```console
python -m learning.multi_agent.step_23d_supervisor_demo
```

先看到 `order → policy → report`；后续更新使用保存的同一个任务 ID，只需再次汇总。不存在的订单跳过政策节点，不给退货判断。候选动作、用户补充是固定结构，未调用真实模型；所有数据在进程退出后消失。

## 常见错误

- 用「未拆封」替代「完好且不影响二次销售」：这两项需要明确核对。
- 用程序的初步条件判断承诺已经退货：示例只有只读工具；即使初步符合，实际仍要验收。
- 把进程内字典说成可跨重启恢复：需要持久化待办、证据与会话隔离，并在恢复时检查过期信息。

## 自测与参考答案

本轮没给订单号时，能把用户补充自动绑定到任意一个待办吗？

<details>
<summary>参考答案</summary>

不能。只在能确定属于同一会话且明确绑定同一订单时更新。多个待办、跨会话、缺少必要证据时先澄清；即使模型猜中，也应由后端守住任务关联和权限。

</details>
