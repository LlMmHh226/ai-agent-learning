# 运行保障 03：一次模型调用的有限重试

## 学习目标

区分短暂失败和持续失败，只在有限次数、有限等待内重试一段模型请求。

## 前置知识

理解 [请求总预算](step_02_request_timeout.md) 以及 [首次模型调用的排错](../../docs/setup.md)。

## 文件职责

[重试示例](step_03_model_retry.py) 构造本地 `APIStatusError`，提取秒数形式的 `Retry-After`，用记录器代替实际等待。它不修改正式聊天模型客户端。

## 具体输入与执行过程

固定 `503`、`Retry-After: 2` → 第一次调用失败 → 判定可重试 → 记录 2 秒等待 → 第二次得到固定回答。有额度错误的 `429`、`401` 或要求等待 80 秒的响应直接结束。第二次仍 `503` 时也结束。

## 运行与预期结果

```console
python -m learning.runtime.step_03_model_retry
```

不访问模型或网络。对照打印的「调用次数、建议等待、结果」；可重试情况最多两次调用。本例只实现秒数头和少量状态码，正式入门调用仍默认不自动重试。

## 常见错误

- SDK 与业务层都重试：两层次数会叠加，重试等待也要计入上层预算。
- 重跑整条业务链：读请求也可能多花费用；涉及订单写操作，须先确认是否执行并有幂等保护。

## 自测与参考答案

为什么同为 `429` 的限流和额度不足不能一律等待再重试？

<details>
<summary>参考答案</summary>

短期限流可能在窗口恢复后解除；额度或账户问题不会靠短暂等待消失。还要尊重服务端建议、剩余预算及尝试次数，避免重复消耗。

</details>
